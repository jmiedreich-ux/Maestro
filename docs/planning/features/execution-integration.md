# Integrate approved work and deliver declared dependencies

## Outcome and result
Closes [Integrate work and deliver declared dependencies](../../outcomes/execution.md#integrate-work-and-deliver-declared-dependencies): independently approved packet revisions enter one durable first-in first-out queue per project; a persistent Integration Manager assembles each into its milestone branch; an independent reviewer checks any new integration code; the service merges without fast-forward and records success only after reading the remote back; and a dependent milestone receives the integrated code it declared through the same queue, with readiness bound to verified commits and invalidated when its source changes.

## Existing implementation assessment
Reused as built: the Execution service and its records, the journaled service-only push, the packet review and correction pattern, the run service and its persistent sessions, the shared owner decision, the terminal's Execution view and the fake-free unit test scaffolding. Gaps found: packets were based on the code baseline and had no milestone branch; approval was the last state, so no dependency could ever be delivered; no queue, milestone records, merge handler, integration roles, dependency records or invalidation existed; the milestone records were never read.

## Decisions
- Milestone records are read and hash-checked at start (or on first use for an Execution begun earlier). A milestone branch `maestro/<activity>/milestone/<milestone>` is created lazily from the recorded code baseline and verified on the remote. A packet branch is now `maestro/<activity>/packet/<packet>`, based on the current milestone head. The installed repository profile must allow `maestro/execution-*`.
- One durable queue per activity holds packet and dependency-import entries in the order the service saw them. Only the head is worked; a blocked head keeps its place and nothing behind it starts.
- The service creates `maestro/<activity>/integration/<entry>` (or `.../dependency/<delivery>`) from the current milestone head, merges the exact approved commit without fast-forward and hands the clone to the Integration Manager, a persistent-session agent that defaults to the Development Manager's route. It resolves conflicts and makes only in-scope fixes; the service checks the result descends from both sides, has no markers and stays inside the assembled packets' permitted paths, then pushes and reads the branch back.
- Integration review is by a configured reviewer that differs from the manager (defaults to the packet reviewers), one targeted correction per round, default limit 2, and the Owner may grant one more through the shared decision. A clean merge with no manager change records evidence and starts no repeat packet review.
- The service merges the integration branch into the milestone branch without fast-forward and pushes without force. A target that moved after preparation sends the entry back for a new attempt and review; earlier records stay.
- A packet dependency on a packet in another milestone is delivered by a dependency delivery: it names the providing milestone head and accumulated packet set, is eligible only when the providing milestone is in the consuming milestone's declared closure, and imports through the queue. Otherwise it is held for source-milestone completion, which belongs to the next outcome. Records carry no separate marker for a dependency that must wait for a completed milestone, so packet dependencies are early by default and milestone dependencies bind completion.
- A delivery whose source is no longer contained in the providing branch is invalidated with its consumers: new starts stop, running results are quarantined, old records stay, and a replacement is queued when the provider is integrated again.
- Milestone quality assurance, promotion to master and completion records are the next outcome.
