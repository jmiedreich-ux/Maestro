# Start Execution and deliver independently reviewed work packets

## Outcome and result
Closes [Deliver independently reviewed work packets](../../outcomes/execution.md#deliver-independently-reviewed-work-packets): from the terminal the Owner explicitly starts Execution of a confirmed breakdown; a persistent Development Manager plans which packets run and with which coder; real coders change a real repository in isolated workspaces; the service pushes and verifies each branch; a different agent reviews the exact revision; findings return for correction within the review limit; and the terminal shows plans, progress, questions, review counts and measurements.

## Existing implementation assessment
Reused as built: the agent run service (assignments, recovery allowance, stop, session resume, measurements), Codex and Claude Code transports, the isolated workspace and egress launch path, the architecture activity pattern (step machine, reservation, persistent session, confirmed reference, journaled GitHub access, owner questions and decisions), the process definition service, the schema bundle resolver and the terminal's architecture commands. The request registry already names `execution.start`, `status`, `pause`, `resume`, `stop` and `retry`. Gaps found: no Execution service, records, process definition or `execution@1` bundle exist; the run service has no `qwen` adapter and no coder, manager or packet-reviewer role or response contract; workspaces give an agent no writable copy of the repository; nothing pushes a branch from a workspace; the older `development_manager.py` loop belongs to the earlier packet store and is not used. The `execution/` source folder is empty.

## Decisions
- One Execution service (`service/execution.py`) owns one activity per project, with SQL tables for the activity, packet assignments, agent routes, reviews and the Git journal. The worker calls its `tick`, like the architecture service.
- `execution.start` reads the project's completed architecture activity, requires a confirmed reference that is still the newest confirmed version and the active registration, reads every published packet and milestone record from GitHub at the confirmed commit and checks their hashes against the confirmed listing. It saves the source commit, records the product master head separately, snapshots the `execution` configuration and reserves the project.
- The Development Manager is a persistent-session agent run per planning action. Its structured result names packet launches (packet, coder route, exact model, reason), priorities, blockers and questions. The service validates each launch against saved state (dependencies approved, capacity, one active assignment per packet, route allowed by the packet's capabilities, location and context) and rejects stale ones with reasons. Packet events (approved, failed, limit reached, answer) start the next planning action; the manager is otherwise idle.
- A coder run gets the usual read-only source and inputs plus a writable clone of the assigned branch under `output/work/`, so the installed egress launcher is unchanged. The coder writes `output/plan.json` first; the service saves and shows it as soon as it appears, before the run ends. It never sees a credential. When the run completes the service commits leftover changes with a local author identity, checks the branch base, the commit graph and that every changed path is inside the packet's permitted paths, then pushes the branch with the bound repository profile and reads the remote ref before it records the revision.
- A reviewer is a different agent from the coder's tool and model where the configuration offers one, in a fresh read-only workspace at the exact pushed commit with the diff and the coder's evidence as inputs. It returns `APPROVE` or `REQUEST_CHANGES` with findings. Approval makes only that revision eligible for integration. A completed review consumes a round; the limit is configured (default 2) and grants are Owner decisions through `owner.decision`. Corrections go back to a coder run on the same branch.
- Qwen is the default coder route through a new `qwen` transport (the installed `qwen` CLI against the local Ollama model, isolated like the other tools, result read from `output/response.json`). The manager may pick a configured Codex or Claude coder route directly.
- Integration into milestone branches, milestone QA, gap resolution, pause/stop and recovery beyond the basic stop are other outcomes.
