# Integrated code and dependency delivery — milestone QA plan

Version 1. Manual acceptance procedure specification. Incorporates all [shared QA rules](README.md), including authority, resource binding, evidence, cleanup and the runtime conversion checklist. No checks have run.

## Milestone and controlling outcomes

Applies only to [Integrated code and dependency delivery](../development-milestones.md#integrated-code-and-dependency-delivery). Its allocated packets, integration dependencies and linked pinned project declarations define scope. Read their full acceptance criteria and definitions of done; these concrete scenarios may share evidence but do not waive an unlisted required criterion. Product behavior remains in [architecture](../../../architecture.md#milestone-quality-assurance-and-test-data).

## Entry and setup

Previous milestones accepted; Integration queue, Dependency delivery and Missing specialist support integrated. Later provider-promotion evidence is unavailable until Verified milestone completion; preserve that named shared-acceptance dependency rather than fake it.

Execute the shared setup sequence and record the exact installed candidate, plan/input hashes and resolved resources before the checks. Resource names and script hashes are unresolved implementation/binding inputs, not fabricated values. No new account, host, repository or credential is provisioned by this plan.

## Test inputs and real entry paths

At least two genuinely reviewed sample packet revisions, two sample milestones with an explicit provider/consumer dependency, a controlled code conflict and a missing-specialist request. Use only run-owned QA repository branches; do not insert eligibility/review rows.

Record actual input hashes/lineage and sanitization classification under the shared data rules. Use the real public path named in each check; capture failures as well as successes. Data preparation must not insert the expected result into internal state.

## Required checks

| Check | Procedure | Expected result / essential failure boundary | Required evidence |
|---|---|---|---|
| FIFO delivery | Queue two real approved revisions, block the head using an actual conflict and observe another project/unrelated eligible coding. | One persistent project Integration Manager processes strict FIFO; blocked head is not skipped; unrelated eligible work follows normal policy. | Queue ordering, session/assignment identities, blocked reason and observed work. |
| Connection changes and merge | Integrate the exact packet from current milestone head, make necessary real connection change and use independent integration-change review. | Non-fast-forward history and remote verification agree; new code is independently checked, unchanged packet work not automatically rereviewed. | Before/after graph, changed paths, review and journal. |
| Early dependency import | Deliver eligible integrated provider code whose accumulated packet set fits declared consumer closure; also attempt excess-closure import. | Exact source/import commits and closure bind readiness; excess closure waits. Dependent work starts from imported head, not moving master or a flag. | Provider/consumer histories, closure validation and readiness records. |
| Dependency invalidation | Invalidate actual source evidence through a controlled source replacement/unavailability, then deliver replacement through the real import path. | Affected transitive work and branch-bound evidence become ineligible; running results are quarantined; unaffected work remains valid. Replacement gets required connection review. | Old/replacement references, invalidated closure, import/review and restored readiness. |
| Specialist support | Trigger actual missing guidance, produce a bounded new role/context and independently review/publish its activation; also check applicability of an unchanged role. | Exact validated files bind affected packets; no rewritten confirmed breakdown or unnecessary review for unchanged role. Unavailable routes respect configured fallback and budgets. | Support assignment, separate fidelity review, remote hashes and binding. |
| Unknown Git result and lifecycle | Lose acknowledgment of actual merge/import, restart and reconcile; pause/stop with a blocked queue head. | No duplicate or unverified merge, force-push/rebase/squash; target changes require reconciliation. Settlement cannot skip held/unfinished head. | Remote readback, expected heads, queue/settlement snapshots and durable counts. |

## Completion and correction

Every required check must satisfy the shared PASS boundary on the same exact candidate. A required missing path, missing tool, missing observation or unavailable artifact is UNTESTED and blocks acceptance; an observed behavior defect is FAIL. Use existing correction and affected-rerun rules, not an extra QA approval round. Independent whole-milestone review remains separate and required before promotion.

This accepts integration and early delivery contributions. Completed-provider delivery, promotion dependency enforcement and final invalidation of real QA evidence must also pass the final milestone plan before the full Integration project outcome is claimed.

## Cleanup and reset

Resolve or explicitly retain blocked/unfinished operations; capture branch ancestry, support files and delivery references before stopping owned processes. Keep remote evidence branches and do not reset product history.

Apply the shared reset checklist. Capture evidence before cleanup, record retained/deferred resources and quarantine unsafe or uncertain environments. Do not destroy evidence or widen cleanup scope to obtain a clean result.
